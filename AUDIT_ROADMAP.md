## 1. Écarts d'architecture entre le code et la roadmap

- **Student≠Enrollment / Teacher≠TeachingAssignment (V0.5) non respecté** : `StudentProfile.classId` (mutable, écrasé) est la vraie source de vérité, pas `Enrollment` (String libres sans FK, périphérique MINESEC). `TeachingAssignment` et `Class` eux-mêmes n'ont **aucun champ année scolaire** — rien dans le schéma ne year-scope l'affectation enseignant↔classe↔matière comme la roadmap le prescrit.
- **Template Engine (V0.4) à une seule application** : pas de `TemplateVersion`/`TemplateConfiguration`, le template est appliqué une fois à l'activation et jamais réappliqué — la règle « override jamais écrasé » n'a donc rien à protéger, et V2.2 (« config locale > template ») est de fait sans objet, confirmé absent.
- **Scheduling Engine (V2.5) architecturalement différent de la spec technique validée** : aucune trace d'OR-Tools/CP-SAT/WASM ; à la place, un algorithme glouton maison (`TimetableAutoController`) fait le travail, non testé, sans gestion de conflit de salle. Du code mort et cassé (`generateTimeTable` dans Inngest, référence un modèle Prisma inexistant) reste enregistré dans `serve()`.
- **Frontière V1.5/V2.5 déjà franchie** : un début d'automatisation (`TimetableAutoController.autoGenerate/adjust`) existe alors que V1.5 doit rester strictement manuel selon la roadmap.
- **V1.7 inversé par rapport à la prescription** : un `GradingEngine` générique bien testé existe mais est **du code mort** ; le calcul réellement utilisé en production vit dans une méthode privée non testée d'un controller HTTP (mauvaise couche + absence de test), exactement l'inverse de ce que la roadmap recommandait d'éviter.
- **Fuites de la couche hexagonale (V0.1)** : plusieurs use cases `application` importent directement des services `infrastructure`, ou prennent `PrismaClient` en constructeur au lieu d'un port/repository.
- **CRUD discipline (V1.9)** codé en handlers Express inline dans `hexagonal.bootstrap.ts`, hors du pattern controller/use case suivi partout ailleurs.
- **Pipeline IA (V3.3) : confirmation utilisateur non généralisée** — le pattern non-négociable de la roadmap (confirmation obligatoire avant persistence) n'est câblé que pour 2 actions destructives sur ~54 ; le reste s'exécute après re-vérification RBAC mais sans confirmation, avec juste un undo a posteriori.
- **Notifications (V2.12) sans moteur de routage** : le canal est toujours codé en dur par l'appelant, aucune logique Urgence→Canal→Préférence→Coût comme demandé.

## 2. Ce qui existe dans le code mais n'apparaît pas dans la roadmap

- **Infrastructure copilote IA substantielle** non documentée : `AIActionAuditLog`+`AISecurityAlert`, `detecterParametreHallucine`, `selectRelevantActions` (sélection dynamique du catalogue par mots-clés pour limiter les tokens), `AssistantConversationTurn` (historique fenêtré), `HelpArticle`/`AssistantHelpQueryLog` (base de connaissances avec escalade humaine).
- **Groupe scolaire déjà largement construit** : `SchoolGroupOwner`/`SchoolGroup`/`GroupTransferRequest` + 3 contrôleurs dédiés (`GroupDashboardController`, `GroupTransferController`, `GroupAuthController`) — bien au-delà du simple concept demandé en V0.2.
- **11 templates d'établissement supplémentaires** au-delà des 8 prioritaires (technique, primaire, maternelle, nursery, bilingue primaire, SAR/SM, CFM).
- **`OnboardingSource.GROUPE_TRANSFERT`** — 4e source d'onboarding non listée dans la roadmap (AUTOSERVICE/CONCOURS/IMPORT_MASSE).
- **`UserArchive`** — mécanisme d'archivage légal avec snapshot JSON complet à la suppression, plus robuste que le simple mot « archivage » de la roadmap.
- **Alertes de retard de programme pédagogique** (`Programme`/`Chapitre`, seuils CRITIQUE/MODERE) — brique pédagogique complète absente du texte fourni.
- **`scanCahier`** — OCR sur photo de cahier de textes papier via `DocumentAiOrchestrator`, fonctionnalité IA non documentée.
- **Onboarding conversationnel piloté par IA** (Groq) pour la configuration d'établissement (`ConfigurerEtablissementUseCase` + wizard), en plus du moteur déterministe par template.
- **`calculerMoyenneSequence` à 3 modes configurables** (`single`/`triple`/`weighted`) par école — une vraie configurabilité non mentionnée.
- **`TimetableAutoController.adjust`** — ajustement d'emploi du temps piloté par instruction en langage naturel (Groq).
- **Barème GCE anglophone à calcul variable par matière** (`GCE_VARIABLES`), au-delà de la simple liste de montants fixes de la roadmap.
- **`ExamRegistration`** avec intégration poussée matricule national + paiement MINESEC, module distinct du concours d'entrée 6e.

## 3. Les 5 zones les plus risquées (données sensibles non testées)

1. **Pipeline de sécurité de l'assistant IA** (`AssistantController.ts` — execute/confirmAction/undoAction, `catalogShared.ts`, 5 catalogues d'actions ~3665 lignes cumulées) : **zéro test** sur la logique qui décide RBAC/hallucination/exécution d'une action IA — seule la journalisation en aval est testée. C'est le point le plus critique de tout l'audit : un bug ici ne casserait pas un test, il agirait silencieusement en production sur de vraies données scolaires.
2. **Calcul de moyenne réellement utilisé en production** (`GradeController.calculerMoyenneSequence`/`calculerMoyenne`, `backend/src/infrastructure/http/controllers/GradeController.ts:916-994`) : aucun test, alors qu'un moteur générique parallèle bien testé (`GradingEngine`) est du code mort qui ne protège rien de ce qui tourne réellement.
3. **Paiements Mobile Money** : `InitierPaiementMobileMoneyUseCase` (déclenche une vraie transaction Campay) non testé, **et** absence totale de mécanisme de conflit de version pour les paiements en offline-sync (V3.2) — alors que la roadmap l'exige explicitement au même titre que les notes.
4. **Permissions / isolation multi-tenant / MFA** : aucun test ne vérifie qu'un token école A ne peut pas accéder aux données école B (isolation au cœur du critère de sortie V0.2) ; `VerifierMfaConnexionUseCase`, `VerifyMfaUseCase`, `VerifyGroupOwnerMfaUseCase`, et la fonction `authorizeSchool` (RBAC `perm:*`) n'ont aucun test — c'est tout le périmètre de sécurité de la plateforme qui repose sur du code non vérifié automatiquement.
5. **`ActiverEtablissementUseCase`** (1073 lignes, transaction Prisma atomique qui génère classes/matières/coefficients/config à l'activation d'un établissement) : zéro test malgré son rôle pivot dans le jalon V0.6 et tout le flux d'onboarding V2.1 — la fonctionnalité la plus complexe du repository n'a aucun filet de sécurité automatisé.

*Mentions complémentaires à surveiller* : idempotence serveur (`middleware/idempotency.ts`, linchpin anti-double-exécution, non testée) ; réorganisation de classes PEBS en masse (`AppliquerTransfertPebsUseCase`, non testée) ; import de masse de données personnelles (`ImporterUtilisateursUseCase`, non testé).
