## 1. Écarts d'architecture entre le code et la roadmap

- **Student≠Enrollment / Teacher≠TeachingAssignment (V0.5) — RÉSOLU** ⟳ : le year-scoping structurel est livré (`Class.academicYearId`, `TeachingAssignment.academicYearId`, `Enrollment` → `InscriptionMinesec`). ⟳ **Chantier 2026-08-20** : `StudentProfile.classId` et `Class.students` sont supprimés du schéma ; `Enrollment` year-scoped (ACTIVE + année courante) est **désormais le pivot du parcours élève**, toute lecture/écriture passant par `studentEnrollment.ts` (`whereProfilesParClasse`, `getClasseActuelleEleve`, `changerClasseEleve`, `inscrireEleve`). 71 fichiers migrés, `tsc --noEmit` propre. `InscriptionMinesec` garde des String libres sans FK — c'est un registre MINESEC distinct, pas le pivot (rôle assumé).
- **Template Engine (V0.4) à une seule application** : pas de `TemplateVersion`/`TemplateConfiguration`, le template est appliqué une fois à l'activation et jamais réappliqué — la règle « override jamais écrasé » n'a donc rien à protéger, et V2.2 (« config locale > template ») est de fait sans objet, confirmé absent.
- **Scheduling Engine (V2.5) — désormais conforme à la spec technique validée** ⟳ : OR-Tools/CP-SAT via `or-tools-wasm`, port `SchedulingSolverPort` + `ORToolsWasmAdapter`, conflit de salle géré, workflow propose/applique atomique. L'écart restant n'est plus architectural mais fonctionnel (contraintes différées, cf. ligne V2.5). Le code mort `generateTimeTable` (Inngest, modèle Prisma inexistant) **reste enregistré dans `serve()`** — non traité.
- ~~**Deux moteurs de génération coexistent**~~ ⟳ **RÉSOLU** : le glouton `autoGenerate` a été supprimé, le solveur CP-SAT est l'unique voie de génération. Seul `adjust` subsiste, comme fonctionnalité d'édition distincte.
- **V1.7 inversé par rapport à la prescription** : un `GradingEngine` générique bien testé existe mais est **du code mort** ; le calcul réellement utilisé en production vit dans une méthode privée non testée d'un controller HTTP (mauvaise couche + absence de test), exactement l'inverse de ce que la roadmap recommandait d'éviter.
- **Fuites de la couche hexagonale (V0.1)** : plusieurs use cases `application` importent directement des services `infrastructure`, ou prennent `PrismaClient` en constructeur au lieu d'un port/repository.
- **CRUD discipline (V1.9)** codé en handlers Express inline dans `hexagonal.bootstrap.ts`, hors du pattern controller/use case suivi partout ailleurs.
- **Pipeline IA (V3.3) : confirmation utilisateur non généralisée** — le pattern non-négociable de la roadmap (confirmation obligatoire avant persistence) n'est câblé que pour 2 actions destructives sur ~54 ; le reste s'exécute après re-vérification RBAC mais sans confirmation, avec juste un undo a posteriori.
- **Notifications (V2.12) sans moteur de routage** : le canal est toujours codé en dur par l'appelant, aucune logique Urgence→Canal→Préférence→Coût comme demandé.

## 3. Les 5 zones les plus risquées (données sensibles non testées)

> ⟳ **4 des 5 zones sont désormais couvertes** (2, 3 partiellement, 1 et 5). Restent ouverts : le
> chemin `/execute` de l'assistant (dépend d'un mock du modèle) et le conflit de version sur les
> paiements offline (manque de conception, pas de test).

1. **Pipeline de sécurité de l'assistant IA** ⟳ **LARGEMENT COUVERT** — 31 tests (`filterCatalogForUser.test.ts`, `assistantSecurite.integration.test.ts`) sur la porte RBAC et sur `confirm-action`/`undo-action`, là où les actions destructives s'exécutent et s'annulent réellement : isolation multi-tenant, re-vérification RBAC serveur, refus d'exécuter une action non destructive par ce canal, gardes d'état, fenêtre d'annulation de 5 min, traçabilité des refus. **Reste non couvert** : le chemin `/execute` lui-même, dont l'issue dépend d'un appel Groq non déterministe — le couvrir suppose de mocker le modèle (décision à prendre). ⟳ L'écart relevé lors de l'écriture des tests (sur la branche sans `allowedRoles`, seule la permission était vérifiée, jamais le rôle) a été **corrigé** : le rôle STAFF est désormais exigé explicitement.
2. ~~**Calcul de moyenne réellement utilisé en production**~~ ⟳ **RÉSOLU** — `gradeController.integration.test.ts` (20 tests, tous au vert) couvre `calculerMoyenneSequence` sur ses 3 modes (single/triple/weighted) avec leurs replis, le plafonnement au barème et le cas « aucune composante → 0, jamais NaN », `calculerMoyenne` (pondération, coefficient 0 exclu, classement), le stampage du coefficient sur les **3 voies d'écriture** (POST, PUT, import Excel) et la répercussion bout-en-bout sur le bulletin. Le `GradingEngine` du domaine n'est **plus** du code mort : `GradeController` l'importe et l'utilise réellement (`calculateAverageScoreOn20`, `scoreOn20ToPercentage`) depuis la suppression du doublon `utils/gradingEngine.ts`. L'inversion signalée en V1.7 n'a donc plus lieu d'être.
3. **Paiements Mobile Money** ⟳ **PARTIELLEMENT RÉSOLU** — `InitierPaiementMobileMoneyUseCase` est désormais couvert (11 tests) : aucun appel Campay émis quand une précondition échoue, montant toujours issu de la facture et jamais de l'appelant, garde anti-double-débit, aucun paiement fantôme après un échec Campay. **Reste entier** : l'absence de détection de conflit de version pour les paiements en synchronisation offline (V3.2), qui est un manque de conception et non de test — la roadmap l'exige pourtant au même titre que les notes.
4. **Permissions / isolation multi-tenant / MFA** ⟳ : l'isolation cross-tenant est désormais testée, mais **seulement sur 3 routes** (`academicYearStructureMultiTenant.integration.test.ts`) — le critère de sortie V0.2 porte sur l'ensemble de l'application et reste donc non démontré. `VerifierMfaConnexionUseCase`, `VerifyMfaUseCase`, `VerifyGroupOwnerMfaUseCase`, et la fonction `authorizeSchool` (RBAC `perm:*`) n'ont toujours aucun test — le périmètre de sécurité de la plateforme reste très majoritairement non vérifié automatiquement.
5. **`ActiverEtablissementUseCase`** ⟳ **COUVERT** — 10 tests (`ActiverEtablissementUseCase.integration.test.ts`) sur les gardes d'entrée, la structure réellement générée (année courante, périodes et séquences, nombre et nommage des classes, matières et coefficients, SchoolConfig, bascule du statut), l'**atomicité sur échec tardif** (vérifiée capable d'échouer : transaction neutralisée → structure orpheline détectée) et la **non-réentrance** (réactivation refusée, aucune duplication). Piège documenté : les niveaux doivent s'écrire `6e`/`5e` comme le wizard les envoie — un libellé approchant crée les classes mais AUCUNE matière, silencieusement.

*Mentions complémentaires à surveiller* : idempotence serveur (`middleware/idempotency.ts`, linchpin anti-double-exécution, non testée) ; réorganisation de classes PEBS en masse (`AppliquerTransfertPebsUseCase`, non testée) ; import de masse de données personnelles (`ImporterUtilisateursUseCase`, non testé).
