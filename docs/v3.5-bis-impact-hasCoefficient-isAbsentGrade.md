- `0.5 ≤ |Δ| <1` : écart 4-6 points → ~20%

### 1.4 Impact sur le rang

Si tous les élèves d'une même classe subissent la **même formule** (tous `true` → tous `false`), l'ordre relatif est-il stable ?

Théorique : Non, pas stable. Exemple classe 3 élèves :
- Avant (`true`, pondéré) : A 11.5, B 10, C 13.33 → rang 1:C, 2:A, 3:B
- Après (`false`, simple) : A 13, B 10, C 13 → rang 1:A/C ex-aequo, 3:B → **A passe devant C**.

**En base réelle :** 0 classe avec notes, donc **0 rang impacté** mesurable. Sur l'échantillon théorique 40 élèves, ~10-15% des rangs bougeraient (ceux avec Δ ≥0.5 et proches voisins).

### 3.1 Un seul commit vs séquencé ?

**4 points de code à toucher** (pas 5) :

2. `GenererBulletinUseCase.ts:124`

4. `catalogShared.ts:212`

**Recommandation : un seul commit** `fix: hasCoefficient/isAbsentGrade — réconciliation V3.5-bis (4 points)` :
- Même formule, même `hasCoefficient=false` pour `FR_PRIMAIRE/EN_PRIMAIRE`/`MATERNELLE`, même `isAbsentGrade` exclu — les 4 doivent basculer ensemble, sinon incohérence durable entre bulletin (pondéré), dashboard (simple), santé (pondéré) et copilot (pondéré sans filtre) pour les mêmes élèves `FR_PRIMAIRE`.
- `isAbsentGrade` est indissociable : si on ne corrige que `hasCoefficient`, `calculerMoyennesClasseSequence` resterait divergent sur l'absent.
- Risque d'un commit unique : aucun, les 4 sont des `calculateAverageScoreOn20(..., hasCoefficient, true)` ou `somme/poids` — même pattern, pas de dépendance d'ordre.
- Alternative séquencée (moteur d'abord, puis 3 autres) n'apporte pas de sécurité supplémentaire et multiplierait les fenêtres d'incohérence.

### 3.2 `GenererBulletinUseCase` — futures générations uniquement

**Oui, faisable sans backfill.** `GenererBulletinUseCase` crée `ReportCard` avec `generalAverage, rank, mention, totalStudents, validationStatus` via `Bulletin.create` + `bulletinRepository.save` sur `classId+academicPeriodId` courants. Le fix ne touche que le calcul avant `save`, pas de migration `UPDATE ReportCard SET generalAverage=... WHERE classWorkflowStatus='PUBLISHED'`. Les bulletins déjà `PUBLISHED`/`SUBMITTED` restent en base avec leur `generalAverage` figé (0 aujourd'hui). Aucun trigger Inngest ne régénère un bulletin publié.

### 3.3 Test de non-régression proposé

**Pour écoles `hasCoefficient=true` (majorité, non affectées) :** `expect(moyenne).toBe(pondérée)` inchangée — un test paramétré `FR_GENERAL_SEC` vs `FR_PRIMAIRE` :
```ts
it('FR_GENERAL_SEC reste pondéré', async () => { expect(compute('s1 FR_GENERAL_SEC', [10,16], [3,1])).toBe(11.5); });

```
Avant/après : `FR_GENERAL_SEC` doit donner **exactement la même valeur** (11.5), `FR_PRIMAIRE` doit **changer** de 11.5 → 13 (documenté comme attendu, pas comme régression).

**Pour `isAbsentGrade` :**
